# G9 调研任务书：用现有计算模块做"AI 做图 + 整版排版"工具的可行性

**用户的问题**：
> 如果拿现在这套计算模块，做一个完整的 **AI 做图 + 排版自动化**工具，难度大不大？输入是**各种不同尺寸的位图 + 矢量图 + 代码或纯数据**，能不能让 **agent 有一个"整体版面"的认识**，并按需求把大图排得**整齐好看**？

**要求**：这是**可行性调研**，不是许愿。必须给:可测/不可测的边界、已知实现与论文、失败模式、以及"哪一部分难到不可做/哪一部分其实很确定"。
共同要求：事实带 URL；本地能核的给路径+行号；【事实】/【推断】分离；**不利结论必须写**；未确证写"未找到"。全文写指定文件；回父代理 ≤500 词摘要。只写该文件，不改仓库其它内容，无 git 写操作。

## 路线 F1 → `docs/research/F1_input_measurability.md`
**不同输入的"可测量性"边界**（这决定整件事的上限）：
1. **矢量**（PDF/SVG）：能提取什么——页面尺寸(mm/pt)、文本及其字号与位置、字体、路径 bbox；工具与精度（PyMuPDF/pdfplumber/svgelements 等，给文档 URL）；**反向问题**：PDF 里的文字不一定还有语义/字形与字号可靠，需注意什么。
2. **位图**：能测到哪一步——像素尺寸 + DPI → 物理尺寸；**字号无法可靠读出**（只能靠 cap-height/OCR 估算，误差多大？）；给出"位图面板只能被摆放，不能被规格归一"的结论证据。
3. **代码/数据**：我们能自己渲染 → 为何这是唯一能保证 `最终尺寸下 k≡1` 的输入；tight bbox 导致"声明≠实测"的处理。
4. **混合输入**的实用结论：agent 必须知道每个面板属于哪一类，以及每类能承诺什么/不能承诺什么。

## 路线 F2 → `docs/research/F2_layout_automation.md`
**自动布局与"整齐好看"能否被操作化**：
1. 现有拼版/布局系统的做法：patchwork/cowplot/egg、FigureGuild、plotstyle、LaTeX subfigures、CSS Grid/Flex 与 Figma auto-layout、约束求解（Cassowary）——各自表达什么约束、能保证什么。
2. **可操作化指标**（把"好看"变成可测代理）：对齐线数量、等距 gutter、基线/视觉重量平衡、留白分布、字号/线宽档位数量、最小字号、无重叠/无越界、面板字母一致性；有没有文献/规范支持这些代理（typographic grid、Gestalt、期刊 checklist）。
3. **已知失败模式**：自动布局做出来"很齐但很丑"的原因；哪些必须人来定（层级、重点、裁剪）。
4. 结论：**规则化布局能覆盖多少比例的"整齐"**；"好看"里哪些可判定、哪些不可判定。

## 路线 F3 → `docs/research/F3_agent_plate_interface.md`
**让 agent 拥有"整体版面认识"的接口与验证闭环**：
1. agent 需要什么表示：面板清单（类型/可测性/物理尺寸/角色/内容摘要）、整版约束（页宽、栏宽、gutter、字号/线宽档位）、可行域（能改什么）与**影响面**（改一处会动到谁）。
2. **plan → apply → measure → repair** 闭环的既有证据（LLM 做布局/图表生成的研究与工程实践；失败模式：幻觉坐标、越界、字号漂移）；必须的护栏（确定性执行、测量回执、拒绝语义）。
3. 现有 agent 工具面对比（Tavotto 的 9 个 MCP 工具已做整版；我们缺什么/可复用 `read_agent_context`）。
4. 结论：**agent 在整版任务里该负责什么、不该负责什么**；最小可用闭环的三个验收。
