# G8：从引擎到产品（易用性 / 兼容性 / Agent 交互）

**现状**：判定与安全很强（测量、真实验证、双状态、漂移检查、原子写、科学指纹、最终尺寸审计），但**引导、发现、回报**很弱。下面每条诊断都有本次会话的实测依据。

---

## 0. 为什么现在"像引擎不像产品"

| 症状 | 依据（本次实测） |
|---|---|
| **第一次使用路径不存在** | wheel 装完只有 `--help`；要用户自己找 `--script/--config`、自己理解 scope/gid，没有"三分钟拿到第一个成功"的路径 |
| **能力发现靠猜** | 能改什么、不能改什么藏在 `layout_contract()` 与拒绝文案里；陌生用户看不到"这张图我能动哪些东西" |
| **契约成本高** | 可编辑性依赖脚本里的 `layout_contract()` / `science_manifest()`——我这轮反复被它绊倒（tick 无绑定、`can_evaluate=false`、标签不可见），用户不改代码就用不上编辑 |
| **没有期刊 preset** | 宽度/字号/线宽要用户自己填（R8 已列为缺口） |
| **没有"体检"命令** | 用户拿到一张图，不知道"离出版还差什么"（现有 final-size 审计只面向多图规格） |
| **拒绝不可行动** | 拒绝是对的，但只给一句原因，没有"要什么条件才能行 / 下一步做什么" |
| **证据不可消费** | 双状态与证据哈希只在内部，外部工具/Agent 拿不到结构化回执 |

---

## 1. 易用性：让陌生用户 3 分钟拿到第一个成功

1. **首跑体验**
   - `figpact ui --example demo`（内置合成例，零参数）；
   - `figpact ui --script my.py`（**无 YAML 也能进只读测量**）；
   - 验收：全新 venv 装 wheel 后，两条命令都能出页面。
2. **能力发现**
   - `figpact capabilities --script x.py` 输出三档清单：**可示范 / 可编辑并保存 / 需作者化 / 不支持**，逐条给原因；
   - 页面侧同样显示（现有 Inspector 已有能力提示，需系统化）。
3. **拒绝可行动**（统一三段式：**为什么不行 / 需要什么才能行 / 一条建议命令**）
   - 五类拒绝都要覆盖：无绑定、绑定歧义、跨 scope、科学锁定、版本漂移。
4. **一键体检**
   - `figpact check --script x.py [--final-width 42mm]`：规格表 + 越界/重叠清单 + 不可行项 + 下一步建议；
   - 这是最能被立刻感知价值的功能（用户第一眼要看的就是"我的图合不合规"）。

---

## 2. 兼容性：让世界上已有的图能用

1. **零契约只读为默认路径**：不写任何代码即可测量/预览/体检。
2. **契约最小化 + 可生成**：`figpact init-contract --script x.py` 产出**最小可编辑声明草稿**（人审后生效），而不是让用户从零写 `layout_contract()`。
3. **按真实脚本逐类支持**（不追求"支持 N 种 AST"）：公开"当前支持哪些写法"的清单，并明确**不支持时的降级行为**。
4. **导出与互操作**：矢量导出 + 与 Tavotto / mpltweak / Illustrator 的交接说明（描边是否随缩放、tight bbox 让声明≠实测这类坑写清）。
5. 验收：仓库内置三类真实脚本（纯 matplotlib / 带 YAML 契约 / 多面板），其"能做与不能做"在 `capabilities` 中如实列出。

---

## 3. Agent 交互：让 Agent 可靠调用，而不是猜

1. **契约化接口**：稳定 JSON schema（输入/输出/错误码）+ 版本号；所有命令支持 `--json`。
2. **回执即证据**：每次操作返回结构化 receipt（双状态 + 证据哈希 + 实测值 + 越界项），**外部工具与 Agent 可直接消费**——这同时是我们与其它编辑器的互操作面。
3. **只读上下文接线**：把已实现的 `read_agent_context`（scene / constraints / impact）接成受控只读端点，Agent **先看再改**。
4. **操作原语可组合且幂等**：`audit / propose / apply / verify / revert`；写操作一律走既有漂移检查 + 原子写 + 写后验证，Agent 只能组合，不能越权。
5. 验收：给一个 20 行 Agent 脚本：读上下文 → 提出位移 → 应用 → 取回执 → 复验，**全程不读源码、不需人类看日志**。

---

## 4. 优先级（按"最快变成可演示证据"排序）

| 级别 | 内容 | 为什么先做 |
|---|---|---|
| **P0** | 零契约只读 + `figpact check` 体检 + 拒绝三段式 | 用户最先用、最易感知；代价最小 |
| **P1** | 能力发现清单 + `init-contract` 草稿 + 内置 demo + 期刊 preset | 把"能用"变成"敢用" |
| **P2** | receipt/schema 稳定化 + Agent 只读端点 + 操作原语 | 让外部（Agent/编辑器）可靠接入 |
| **P3** | 工具侧实测排版能力（标签摆位：测量 bbox × 曲线包络 → 算毫米位移 → 写参数 → 复验） | 把我在演示图里"作弊"的部分搬进引擎，且这是当前没人占住的实测型能力 |

---

## 5. 明确不做

不做多面板拖拽 GUI（mpltweak / Tavotto 的主场）；不做通用 AST 适配军备；不宣称 OS 沙箱；不在没有真实用户前扩建评测规模。

---

## 6. 三个"够到产品级"的判定标准

1. **易用性**：陌生科研人员装完 → **3 分钟内**完成"选一个标注 → 移动 → 保存 → 重跑一致"，**全程不读源码、不改自己的代码**。
2. **兼容性**：拿一张**从未为 figpact 改过**的图，能给出体检报告与能力清单；不支持的部分解释到"我知道下一步该干什么"。
3. **Agent**：外部 Agent 只靠 `--json` + schema 完成"读上下文 → 改 → 验证 → 拿到证据"，无需人类读日志。

（以上三条达成时，才算产品；在此之前都只是引擎。）
